# 프로젝트 차원의 이슈 관리 구현 계획

## 결론

프로토타입 이슈와 프로젝트 이슈는 아예 별도 도메인으로 둔다.

프로토타입 이슈는 말 그대로 개별 프로토타입의 버그/개선/질문을 관리하는 기능이고, 프로젝트 이슈는 메인 업무 프로젝트 차원에서 발생하는 이슈를 업무 관리와 비슷한 방식으로 추적하는 기능이다. 둘 사이에 이관, 승격, 통합 목록, 공통 상태 흐름이 없다면 DB/API/프론트 도메인을 엮을 이유가 없다.

정리하면 다음 방향이다.

- 기존 `issues` 도메인은 프로토타입 이슈 전용으로 유지한다.
- 새 `project_issues` 도메인을 만든다.
- 백엔드도 `src/project-issues/`로 분리한다.
- 프론트도 `entities/project-issue`, `features/project-issue`, `pages/project-issues`로 분리한다.
- 업무 관리와는 UX/컴포넌트 패턴만 참고한다.
- `tasks`에 섞지 않고, 기존 프로토타입 `issues`에도 섞지 않는다.

## 도메인 구분

| 구분 | 프로토타입 이슈 | 프로젝트 이슈 |
|---|---|---|
| 목적 | 개별 프로토타입 피드백/버그/개선 추적 | 프로젝트 운영 중 발생하는 이슈/리스크/개선/질문 추적 |
| 기존/신규 | 기존 `issues` 유지 | 신규 `project_issues` 추가 |
| 대상 | `prototypeId` 필수 | `projectId` 필수 |
| URL | `/issues?prototypeId=...` | `/project-issues?projectId=...` |
| UI | 프로토타입 상세에서 진입 | 프로젝트/업무 관리 영역에서 진입 |
| 상호 연결 | 없음 | 없음 |

## 목표

- 프로젝트 단위 이슈 목록을 `/project-issues?projectId={projectId}`에서 관리한다.
- 업무 관리처럼 테이블/칸반/카드 뷰를 제공한다.
- 검색, 상태, 유형, 우선순위, 담당자, 마감일, 보관/복원을 지원한다.
- 상세에서 체크리스트, 첨부, 댓글, 활동 로그를 관리한다.
- 기존 프로토타입 이슈 기능은 건드리지 않는다.

## 핵심 설계

### 1. 별도 도메인

프로젝트 이슈는 신규 도메인으로 만든다.

- DB: `project_issues`, `project_issue_comments`, `project_issue_checklists`, `project_issue_attachments`, `project_issue_activity_logs`
- Backend: `src/project-issues/`
- Frontend entity: `src/entities/project-issue/`
- Frontend feature: `src/features/project-issue/`
- Page: `src/pages/project-issues/`

### 2. 업무 관리와의 관계

업무 관리와 같은 경험을 제공하되 데이터는 분리한다.

재사용/참고:

- `TaskPage`의 검색/필터/상태 카운트/뷰 전환 구조
- `TaskTableView`, `TaskKanbanView`, `TaskCardView`의 UX 패턴
- `TaskDetailDialog`의 탭 구조
- 체크리스트/댓글/첨부/activity API 설계

분리:

- `tasks` 테이블에 넣지 않는다.
- `task_*` 하위 테이블을 재사용하지 않는다.
- 업무 상태 enum과 프로젝트 이슈 상태 enum을 섞지 않는다.

### 3. 기능 범위

1차 포함:

- 프로젝트 이슈 CRUD
- 테이블/칸반/카드 뷰
- 검색, 상태, 유형, 우선순위, 담당자 필터
- 상태 변경, 우선순위 변경, 담당자 변경
- 수동 순서 변경
- 보관/복원
- 댓글
- 체크리스트
- 첨부
- 활동 로그

1차 제외:

- 프로토타입 이슈와 프로젝트 이슈 연결
- 프로젝트 이슈와 업무(`tasks`) 연결
- 이슈를 업무로 변환
- 전체 프로젝트 통합 대시보드
- 실시간 WebSocket 업데이트

## 추천 라우트

- `/project-issues?projectId={projectId}`: 프로젝트 이슈 관리
- 후순위: `/project-issues/all`: 전체 프로젝트 이슈 통합 보기

기존 `/issues?prototypeId={prototypeId}`는 프로토타입 이슈 전용으로 계속 둔다.

## 구현 순서 요약

1. 기존 프로토타입 `issues`는 변경하지 않는 기준을 확정한다.
2. `project_issues` 계열 DB 테이블을 새로 추가한다.
3. `ProjectIssuesModule` 백엔드 API를 구현한다.
4. `entities/project-issue` 타입/API와 query hook을 추가한다.
5. `features/project-issue` UI를 업무 관리 UX 기준으로 만든다.
6. `/project-issues` route와 프로젝트 영역 진입 버튼을 붙인다.
7. 타입체크, 빌드, 브라우저 검증을 진행한다.
