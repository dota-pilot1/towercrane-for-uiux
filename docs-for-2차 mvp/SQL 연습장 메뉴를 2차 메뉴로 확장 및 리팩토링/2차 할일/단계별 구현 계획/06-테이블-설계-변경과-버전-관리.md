# 6단계 - 테이블 설계 변경과 버전 관리

## 목표

유저 연습장의 커머스 DB 테이블 설계를 바꿀 수 있게 하되, 기존 문제가 깨지지 않도록 version으로 관리한다.

추후 유저나 관리자가 sqlite 파일 자체를 교체하는 기능도 이 단계의 확장으로 다룬다.

## 정책

- 활성 schema version은 하나만 둔다.
- 테이블 설계를 바꾸면 기존 schema를 직접 수정하지 않고 새 version을 만든다.
- sqlite 파일 교체는 사용자 경험상 현재 파일 덮어쓰기로 제공한다.
- 내부적으로는 기존 schema를 보존하고 새 version을 만든다.
- 기존 문제는 생성 당시 schema version에 계속 연결된다.
- 새 문제는 현재 활성 schema version에 연결된다.
- 기존 제출 기록은 재채점하거나 새 version으로 이동하지 않는다.

## 왜 version이 필요한가

문제는 특정 테이블/컬럼에 의존한다. 테이블 이름이나 컬럼이 바뀌면 기존 문제가 바로 깨질 수 있다.

따라서 테이블 설계 변경은 “현재 DB를 수정”하는 기능이 아니라 “새 스키마 버전을 발행”하는 기능으로 다뤄야 한다.

파일 교체도 같은 원칙을 적용한다. 사용자에게는 현재 DB 파일을 덮어쓰는 기능처럼 제공한다. 다만 내부적으로 기존 schema를 실제 삭제하거나 기존 문제의 기준 DB를 바꾸면 제출 기록의 의미가 사라질 수 있으므로, 파일 교체는 새 schema version 생성 이벤트로 처리한다.

## 파일 교체 정책

```text
현재 schema v1
- 문제 A
- 문제 B
- 제출 기록

sqlite 파일 교체
→ schema v2 생성
- 새 문제 C
- 새 문제 D
```

- v1 문제와 제출은 v1에서 계속 조회/실행한다.
- v2가 활성 schema가 되면 새 문제는 v2에 연결한다.
- v1 문제를 v2로 옮기고 싶으면 복제 기능을 사용한다.
- 복제 시 대상 테이블/컬럼이 존재하는지 호환성을 확인한다.
- 파일 hash를 저장해 같은 파일 중복 업로드를 막는다.

## UX 초안

```text
테이블 설계 관리
- 현재 스키마 보기
- 새 버전 만들기
- sqlite 파일로 새 버전 만들기
- DDL 편집
- 샘플 데이터 편집
- ERD 미리보기
- 활성화
```

## MVP에서는 미룰 수 있는 것

- 자유로운 GUI 테이블 빌더
- 컬럼 단위 diff 뷰
- 자동 migration
- 여러 스키마 동시 운영 UI
- sqlite 파일 교체 UI

초기에는 DDL SQL 편집과 검증으로 시작한다.

## 완료 기준

- 새 schema version을 만들 수 있다.
- 새 version 기준 runtime DB가 생성된다.
- 기존 문제는 기존 schema version에서 계속 실행된다.
- 추후 sqlite 파일 교체도 새 schema version 생성 방식으로 붙일 수 있다.
