# 07. 나중에 보완할 항목

## 목적

SQL 파일 덮어쓰기 MVP 구현 이후 안정성과 정책 명확성을 위해 보완할 항목을 정리한다.

아래 항목은 초기 구현을 막는 필수 조건은 아니지만, 운영 품질을 높이려면 후속으로 확정하는 것이 좋다.

## 1. 파일 크기 제한 값 명시

현재 계획에는 "파일 크기 제한 확인"만 있고 구체적인 숫자가 없다.

후속 결정 필요:

```text
MVP 권장값: 2MB
상한 후보: 2MB / 5MB / 10MB
```

권장:

- MVP는 `2MB`로 시작한다.
- 실제 seed SQL이 커질 가능성이 있으면 `5MB`까지 허용한다.
- `10MB` 이상은 업로드/검증/런타임 DB 생성 비용을 보고 별도 판단한다.

반영 위치:

- `multer` limits
- service file size validation
- 프론트 다이어로그 안내 문구

예:

```ts
FileInterceptor('file', {
  limits: {
    fileSize: 2 * 1024 * 1024,
  },
})
```

## 2. 임시 runtime DB cleanup

현재 계획은 metadata transaction 범위만 명시한다.

명시된 transaction:

- schema version insert
- workspace active schema version update

보완 필요:

- SQL 검증 중 생성한 임시 runtime DB 파일 정리
- 검증 실패 시 임시 파일 삭제
- 검증 성공 후에도 임시 runtime user id로 만든 DB 파일을 유지할지 삭제할지 정책 결정

권장:

- 검증용 임시 DB는 성공/실패와 관계없이 삭제한다.
- 실제 사용 runtime DB는 새 schema version을 active로 만든 뒤 요청 시 lazy 생성한다.

반영 위치:

- `replacePersonalPracticeSchemaVersion`
- `validatePersonalSchemaSql`
- `try/finally` cleanup

예:

```ts
try {
  // apply uploaded SQL to temp DB
  // introspect tables
} finally {
  this.removeRuntimeDatabase(tempRuntimeUserId)
}
```

주의:

- 기존 사용자의 active runtime DB를 삭제하면 안 된다.
- 기존 schema version runtime DB도 기존 문제/공유 링크가 쓸 수 있으므로 삭제하면 안 된다.

## 3. dbFileHash 충돌 정책

같은 내용의 SQL 파일을 다시 업로드했을 때 어떻게 처리할지 정책이 필요하다.

선택지:

### A. 같은 hash면 409 거부

장점:

- 중복 version 방지
- version history가 깔끔함

단점:

- 사용자는 "다시 적용"하고 싶은데 막힐 수 있음
- title/description만 바꿔 올리는 경우도 막힘

### B. 같은 hash여도 새 version 생성

장점:

- 구현 단순
- 사용자의 교체 시도를 그대로 기록
- title/description을 다르게 남길 수 있음

단점:

- 같은 DB 내용의 version이 여러 개 생길 수 있음

권장:

MVP는 `B. 같은 hash여도 새 version 생성`으로 간다.

이유:

- 파일 교체 기능의 핵심은 active version 전환이다.
- 중복 방지는 나중에 version history 화면이 생긴 뒤 UX와 같이 결정하는 편이 낫다.

나중에 version history가 생기면 같은 hash 표시만 해도 된다.

## 4. react-query invalidate 범위 축소

현재 계획은 MVP 안정성을 위해 넓은 invalidate를 허용한다.

```ts
queryClient.invalidateQueries({
  queryKey: ['sql-practice'],
})
```

장점:

- 누락 없이 화면이 갱신됨
- 구현 단순

단점:

- 같은 페이지의 다른 SQL practice 데이터까지 refetch될 수 있음
- workspace가 여러 개 생기면 불필요한 네트워크 요청 증가

후속 개선:

workspace 단위 key만 무효화한다.

예:

```ts
queryClient.invalidateQueries({
  queryKey: sqlPracticeQueryKeys.personalDefaultWorkspace(),
})
queryClient.invalidateQueries({
  queryKey: sqlPracticeQueryKeys.personalMeta(workspaceId),
})
queryClient.invalidateQueries({
  queryKey: sqlPracticeQueryKeys.personalTables(workspaceId),
})
queryClient.invalidateQueries({
  queryKey: sqlPracticeQueryKeys.personalErd(workspaceId),
})
queryClient.invalidateQueries({
  predicate: (query) =>
    query.queryKey[0] === 'sql-practice' &&
    query.queryKey.includes('personal-problems') &&
    query.queryKey.includes(workspaceId),
})
```

권장:

- MVP: 넓게 invalidate
- 후속: workspace 단위로 축소

## 정리

초기 구현에서는 다음 정책으로 시작한다.

```text
파일 크기 제한: 2MB 권장, 구현 시 숫자 확정
임시 DB cleanup: try/finally로 삭제
동일 hash 업로드: 새 version 생성 허용
query invalidate: MVP는 넓게, 후속으로 workspace 단위 축소
```
