# 업무 관리 개인용 페이지 따로 추가 하기 구현 계획

## 결론

구현 가능하다. 현재 업무 관리 기능은 이미 `tasks.assigneeId` 기반 담당자 필터, 상태/우선순위/보관/댓글/체크리스트/첨부 API, 테이블/칸반/카드 UI를 갖고 있다. 따라서 “전체 업무”와 “~의 업무”를 완전히 별도 도메인으로 새로 만들기보다, 업무 도메인은 하나로 유지하고 메뉴/라우트/쿼리 scope만 분리하는 방식이 가장 적합하다.

데이터 삭제와 DB 재설계가 가능하다는 전제이므로, 기존 `tasks` 관련 테이블을 유지 보수식 ALTER로 누적하기보다 새 스키마 기준으로 정리하고 SQLite 데이터를 초기화한 뒤 재시드하는 방향으로 진행한다.

## 목표 화면

- 1차 메뉴: `업무 관리`
- 2차 메뉴:
  - `전체 업무`: 기존 `/task` 화면의 역할. 모든 업무를 보고 담당자 필터로 좁힌다.
  - `내 업무`: 현재 로그인 사용자가 담당자인 업무를 기본으로 보여준다.
  - 선택 확장: `오현석의 업무`, `정현우의 업무`처럼 특정 사용자 업무를 바로 여는 URL 또는 사용자 선택 뷰.

## 추천 라우트

- `/task`: 전체 업무
- `/task/my`: 내 업무
- `/task/users/$userId`: 특정 사용자의 업무

`/task`는 기존 북마크와 메뉴 호환을 위해 유지한다. `sectionId`는 메뉴 시스템에 맞춰 다음처럼 추가한다.

- `task_all` -> `/task`
- `task_my` -> `/task/my`
- `task_user` 또는 `task_users` -> `/task/users/$userId` 직접 메뉴로 쓰기보다는 페이지 내부 사용자 선택에 사용

## DB 설계 방향

현재 핵심 컬럼:

- `tasks.reporterId`: 작성자
- `tasks.assigneeId`: 담당자
- `tasks.archived`: 보관 여부
- `task_checklists`, `task_comments`, `task_attachments`, `task_activity_logs`: 업무 하위 데이터

추가/정리 권장 컬럼:

- `tasks.scope`: `TEAM` | `PERSONAL`
  - 전체 업무와 개인 업무를 데이터 성격으로도 구분할 수 있게 한다.
  - “내 업무”는 기본적으로 `assignee_id = currentUser.id`를 사용하되, 개인 메모성 업무까지 허용하려면 `scope = PERSONAL AND owner_id = currentUser.id`도 포함한다.
- `tasks.ownerId`: 개인 업무 소유자
  - 개인 업무의 주인. 팀 업무는 `NULL` 허용.
- `tasks.visibility`: `TEAM` | `PRIVATE`
  - 팀 전체 업무와 비공개 개인 업무 권한을 분리한다.
- 인덱스:
  - `(archived, status, order_idx)`
  - `(assignee_id, archived, status, order_idx)`
  - `(owner_id, archived, status, order_idx)`
  - `(scope, archived, updated_at)`

MVP에서는 `scope`, `ownerId`, `visibility`를 추가하되, 개인 페이지의 기본 조건은 `assigneeId = currentUser.id`로 시작한다. 그래야 기존 담당자 기반 업무 관리 UX와 충돌하지 않는다.

## API 설계 방향

기존 `GET /tasks`에 query를 확장한다.

- `scope=all`: 전체 업무. 관리자/일반 사용자 모두 접근 가능하되 `PRIVATE` 개인 업무는 제외.
- `scope=my`: 현재 로그인 사용자의 업무. `assigneeId = me` 또는 `ownerId = me`를 포함.
- `scope=user&userId={id}`: 특정 사용자의 업무. 팀 가시성 업무 중 해당 사용자가 담당자인 업무.

별도 endpoint를 늘리는 것보다 `GET /tasks` query를 확장하는 편이 기존 `taskApi.list`, `useTasks`, 테이블/칸반/카드 컴포넌트를 그대로 재사용하기 좋다.

쓰기 정책:

- 팀 업무 생성: `scope=TEAM`, `visibility=TEAM`, `reporterId=currentUser.id`, `assigneeId` 선택.
- 개인 업무 생성: `scope=PERSONAL`, `visibility=PRIVATE` 기본, `ownerId=currentUser.id`, `assigneeId=currentUser.id` 기본.
- 관리자는 전체 팀 업무 수정 가능.
- 일반 사용자는 작성자/담당자/개인 업무 소유자일 때 수정 가능.

## 프론트 설계 방향

`TaskPage`를 mode 기반 페이지로 바꾼다.

- `TaskPage mode="all"`: 전체 업무
- `TaskPage mode="my"`: 내 업무
- `TaskPage mode="user"`: 특정 사용자 업무

또는 `TaskPage` 내부에서 라우트 params/search를 읽어 `taskScope`를 계산한다. 기존 `TaskToolbar`, `TaskTableView`, `TaskKanbanView`, `TaskCardView`, `TaskDetailDialog`, `TaskFormDialog`는 최대한 재사용한다.

UI 변경:

- 페이지 헤더 제목:
  - 전체 업무: `전체 업무`
  - 내 업무: `{userName}의 업무`
  - 특정 사용자: `{targetUserName}의 업무`
- 전체 업무 화면은 담당자 필터 유지.
- 내 업무 화면은 담당자 필터를 기본 숨김 또는 “내 업무 고정” 상태로 표시.
- 개인 업무 생성 시 담당자를 로그인 사용자로 기본 선택하고, 필요하면 팀 업무로 전환하는 segmented control을 제공한다.

스타일 주의:

- raw Tailwind 팔레트 금지.
- `text-text-primary`, `text-text-secondary`, `bg-surface-muted`, `border-surface-border-soft`, `ui-panel-soft`, `ui-icon-button` 등 semantic token과 `ui-*` 유틸만 사용한다.

## 메뉴 설계

현재 메뉴는 `menus` 테이블의 parent/children 구조와 `sectionIdToPath()` 매핑으로 동작한다. `업무 관리`를 dropdown parent로 바꾸고 하위 메뉴를 추가한다.

- parent: `업무 관리`, `sectionId = task_group` 또는 `NULL`, `icon = CheckSquare`
- child 1: `전체 업무`, `sectionId = task_all`, `icon = ListChecks`
- child 2: `내 업무`, `sectionId = task_my`, `icon = UserCheck`

프론트 매핑 추가:

- `task_group`은 직접 이동하지 않음.
- `task_all` -> `/task`
- `task_my` -> `/task/my`
- `/task`, `/task/my`, `/task/users/*` 모두 active section은 업무 관리 계열로 잡는다.

## 데이터 초기화 전략

사용자가 데이터 삭제를 허용했으므로 개발 중에는 다음 전략을 우선한다.

1. 새 Drizzle schema 작성.
2. 새 migration 생성.
3. 로컬 SQLite 파일 삭제 또는 tasks 관련 테이블 drop 후 재생성.
4. seed에서 메뉴와 샘플 업무를 새 구조로 재삽입.

주의: 로그인 테스트를 위해 `users`, `sessions`, 기본 관리자/테스트 유저 seed는 유지하거나 재생성한다.

## 구현 순서

1. DB 스키마와 seed/menu 구조 정리.
2. 백엔드 `tasks` query scope, 권한, DTO 확장.
3. 프론트 타입/API/query key 확장.
4. 라우터와 헤더 section mapping 확장.
5. `TaskPage`를 scope-aware 페이지로 개편.
6. 생성/수정 dialog에 팀/개인 업무 기본값 반영.
7. 빌드, 타입체크, 브라우저 확인.

세부 파일별 단계는 `단계별 계획` 디렉터리의 문서를 따른다.
