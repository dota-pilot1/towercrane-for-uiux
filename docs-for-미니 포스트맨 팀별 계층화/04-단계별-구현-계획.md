# 04. 단계별 구현 계획

## Phase 0. 현재 구현 정리

목표: 팀 계층 추가 전에 현재 Postman Lite의 기준선을 잡는다.

작업:

- 현재 `/api-doc` 화면에서 컬렉션 생성, API 항목 생성, 저장, Send가 정상 동작하는지 확인
- JSON import/export가 현재 DB 구조와 맞는지 확인
- `api_doc_categories`, `api_doc_endpoints`, `api_doc_blocks`에 기존 데이터가 있는지 확인
- raw Tailwind 팔레트가 새로 추가된 Postman 코드에 없는지 확인

완료 기준:

- 현재 기능을 깨뜨리지 않는 기준 테스트 목록이 생긴다.

## Phase 1. 팀 워크스페이스 최소 구현

목표: "특정 팀의 Postman"이라는 최상위 구조를 만든다.

백엔드:

- `api_doc_teams` 테이블 추가
- `api_doc_categories.team_id` 추가
- 기존 category를 기본 팀으로 마이그레이션
- 팀 CRUD API 추가
- 팀별 category 조회 API 추가

프론트:

- `ApiDocTeam` 타입 추가
- team query hook 추가
- `ApiWorkspaceHome` 추가
- `ApiWorkspaceCard` 추가
- 워크스페이스 카드 클릭 시 해당 팀 Postman Lite 화면 진입
- Postman Lite 상단에 워크스페이스 홈으로 돌아가는 버튼 추가
- 선택된 팀 기준으로 collection 목록 조회
- 팀이 바뀌면 selected category/request 초기화

완료 기준:

- `/api-doc` 첫 화면에 워크스페이스 카드 목록이 보인다.
- 워크스페이스 카드를 누르면 해당 팀의 Postman Lite 화면이 열린다.
- 팀마다 컬렉션 목록이 분리된다.
- 기존 컬렉션은 기본 팀에 보인다.

## Phase 2. import/export를 팀 단위로 확장

목표: 팀별 Postman 스펙을 파일로 주고받을 수 있게 한다.

백엔드:

- `GET /api-doc/teams/:teamId/export`
- `POST /api-doc/teams/:teamId/import`
- version 1 JSON은 선택된 팀에 append
- version 2 JSON은 team 정보를 포함해 import

프론트:

- import/export 버튼이 selected team을 기준으로 동작
- export 파일명에 team name 포함
- import 완료 후 해당 팀의 category/endpoints query invalidate

완료 기준:

- 팀 하나만 JSON으로 내보낼 수 있다.
- 같은 파일을 다른 팀에 가져올 수 있다.
- 기존 version 1 import 파일도 계속 동작한다.

## Phase 3. 폴더/시나리오 계층 추가

목표: 컬렉션 안에서 요청을 시나리오 단위로 묶는다.

백엔드:

- `api_doc_folders` 테이블 추가
- `api_doc_endpoints.folder_id` 추가
- 폴더 CRUD/reorder API 추가
- 폴더별 endpoint 조회 API 추가

프론트:

- 2번째 컬럼을 요청 목록에서 folder/request tree로 확장
- 폴더 생성/수정/삭제/정렬 UI 추가
- 폴더 없는 요청은 "미분류" 그룹에 표시

완료 기준:

- 컬렉션 안에 폴더를 만들 수 있다.
- 요청을 폴더 안에 생성할 수 있다.
- 기존 요청은 미분류로 보인다.

## Phase 4. 팀 권한 모델 추가

목표: 팀별 편집 권한을 분리한다.

백엔드:

- `api_doc_team_members` 테이블 추가
- owner/editor/viewer role 추가
- 팀별 조회 권한 필터링
- 편집 API에 팀 권한 검사 추가

프론트:

- 팀 멤버 관리 UI는 후순위로 두고, 우선 role에 따라 버튼 노출만 제어
- `isAdmin || teamRole === 'owner' || teamRole === 'editor'`이면 편집 가능
- viewer는 Send와 조회만 가능

완료 기준:

- 일반 사용자는 권한 있는 팀만 볼 수 있다.
- viewer는 팀/컬렉션/API를 수정할 수 없다.

## Phase 5. 팀별 환경 변수

목표: 팀마다 local/dev/prod API base를 따로 관리한다.

백엔드:

- `api_doc_environments` 테이블 추가
- 팀별 environment CRUD API 추가
- secret 값 저장 정책은 별도 결정

프론트:

- 현재 localStorage 환경 변수 구조와 팀 환경을 병합
- 팀 환경 값이 기본값이 되고, 개인 local override를 허용
- `{{API_BASE}}`, `{{TOKEN}}` 치환 로직은 유지

완료 기준:

- 팀을 바꾸면 기본 `API_BASE`가 바뀐다.
- 개인 token은 팀 export에 포함되지 않는다.

## Phase 6. 리팩토링과 명칭 정리

목표: 코드의 개념 이름을 실제 UI 용어에 맞춘다.

작업:

- `ApiDocCategory`를 `ApiDocCollection` alias로 감싼다.
- `ApiDocEndpoint`를 `ApiDocRequest` alias로 감싼다.
- UI 텍스트의 "API 항목"을 "Request" 또는 "요청"으로 정리한다.
- 반복되는 sidebar/tree item을 `shared/ui` 또는 `features/api-doc/ui` 컴포넌트로 분리한다.

완료 기준:

- 새 기능 코드에서 category/endpoint라는 DB 용어가 UI 컴포넌트 바깥으로 새지 않는다.

## 권장 구현 순서 요약

```text
1. 팀 테이블 + team_id
2. 워크스페이스 카드 첫 화면
3. 팀별 import/export
4. 폴더/시나리오
5. 팀 권한
6. 팀별 환경 변수
7. 명칭 정리
```

실제 개발은 1, 2, 3까지만 먼저 묶어도 충분히 사용성이 좋아진다.
