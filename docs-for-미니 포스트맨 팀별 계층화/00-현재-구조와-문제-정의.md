# 00. 현재 구조와 문제 정의

## 현재 구현

현재 `/api-doc` 화면은 아래 구조다.

```text
api_doc_categories
  api_doc_endpoints
    api_doc_blocks(block_type = API, content = ApiBlockContent JSON)
```

프론트 화면은 3분할이다.

```text
컬렉션 목록 | API 항목 목록 | 요청 편집/테스트 패널
```

관련 파일:

- `towercrane-for-uiux-front/src/pages/api-doc/ui/api-doc-page.tsx`
- `towercrane-for-uiux-front/src/features/api-doc/ui/api-tester-panel.tsx`
- `towercrane-for-uiux-front/src/entities/api-doc/model/types.ts`
- `towercrane-for-uiux-server/src/api-doc/api-doc.controller.ts`
- `towercrane-for-uiux-server/src/api-doc/api-doc.service.ts`
- `towercrane-for-uiux-server/src/database/schema.ts`

## 현재 구조의 한계

### 1. 컬렉션이 최상위라 팀 맥락이 없다

`Auth`, `Chatbot`, `Board` 같은 컬렉션은 어느 팀의 API인지 구분하기 어렵다. 팀별로 API 소유권, 테스트 목적, 환경 변수가 달라지면 현재 구조에서는 이름 앞에 팀명을 붙이는 방식밖에 없다.

```text
AI팀 Auth
AI팀 Chatbot
Admin팀 Auth
Admin팀 Board
```

이 방식은 목록이 길어질수록 탐색성이 떨어진다.

### 2. 환경 변수가 전역 localStorage 기준이다

현재 환경 변수는 프론트 localStorage 중심이다. 팀별로 `API_BASE`, `TOKEN`, `ADMIN_TOKEN`, `DEV_BASE`, `PROD_BASE`가 달라질 수 있는데, 이를 전역으로 두면 팀을 바꿀 때마다 환경 값을 손으로 맞춰야 한다.

### 3. import/export 단위가 전체 또는 컬렉션 중심이다

팀 단위 백업, 팀 단위 공유, 특정 팀 스펙만 가져오기 같은 업무 흐름이 어렵다.

### 4. 폴더/시나리오 계층이 없다

Postman을 실제로 쓰는 방식은 단순 컬렉션 안에 요청을 나열하는 것보다 시나리오 단위가 많다.

```text
Auth
  01. 회원가입
  02. 로그인
  03. 토큰 갱신
  04. 로그아웃
```

현재는 이 계층을 표현할 필드가 없다.

## 개선 방향

상위 개념을 "특정 팀의 Postman"으로 잡는다.

```text
Team Workspace
  Collection
    Folder or Scenario
      Request
```

1차에서는 팀 워크스페이스만 추가하고, 기존 category를 collection으로 유지한다. 2차에서 folder/scenario를 추가한다. 3차에서 팀별 권한과 환경 변수 저장을 확장한다.
