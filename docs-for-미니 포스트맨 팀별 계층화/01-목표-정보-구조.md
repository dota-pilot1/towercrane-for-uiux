# 01. 목표 정보 구조

## 핵심 개념

| 개념 | 의미 | 예시 |
|---|---|---|
| Team Workspace | 특정 팀의 Postman 공간 | AI 서비스 포털 팀, 운영 Admin 팀 |
| Collection | 업무 도메인 또는 API 묶음 | Auth, Chatbot, Board, Menu Admin |
| Folder/Scenario | 요청 흐름 또는 하위 기능 묶음 | 로그인 플로우, 세션 관리, 게시글 CRUD |
| Request | 실제 API 요청 | `POST /auth/login` |
| Request Spec | Params, Headers, Body, Auth, Response 저장 JSON | `ApiBlockContent` |

## 권장 계층

```text
api_doc_teams
  api_doc_collections
    api_doc_folders
      api_doc_requests
        api_doc_blocks
```

다만 현재 DB에 이미 아래 테이블이 있으므로, 즉시 이름을 바꾸지 않는다.

```text
api_doc_categories = collections 역할
api_doc_endpoints = requests 역할
api_doc_blocks = request spec 역할
```

## 단계별 매핑

### 1차 매핑

팀만 추가한다.

```text
api_doc_teams
  api_doc_categories
    api_doc_endpoints
      api_doc_blocks
```

`api_doc_categories.team_id`를 nullable로 추가한 뒤 기존 데이터는 `Default Team`에 연결한다.

### 2차 매핑

폴더를 추가한다.

```text
api_doc_teams
  api_doc_categories
    api_doc_folders
      api_doc_endpoints
        api_doc_blocks
```

`api_doc_endpoints.folder_id`는 nullable로 시작한다. 폴더 없는 요청도 허용해서 기존 데이터를 그대로 보여줄 수 있게 한다.

### 3차 매핑

이름을 업무 용어에 맞춰 정리한다. 실제 DB rename은 선택 사항이다.

```text
category -> collection
endpoint -> request
block -> request spec
```

코드에서는 타입 alias부터 먼저 도입한다.

```ts
type ApiDocCollection = ApiDocCategory
type ApiDocRequest = ApiDocEndpoint
```

## 추천 기본 팀

초기 seed는 아래처럼 만든다.

```text
Prototype Console
  Auth
  Chatbot
  Task
  Board
  SQL Practice
  Admin
```

나중에 실사용 기준으로 다음처럼 분리할 수 있다.

```text
AI 서비스 포털 팀
운영 Admin 팀
학습/챌린지 팀
데이터/SQL Practice 팀
```

## 선택 상태 모델

프론트 선택 상태는 아래 순서로 좁혀진다.

```ts
selectedTeamId
selectedCollectionId
selectedFolderId
selectedRequestId
```

폴더가 없는 1차에서는 `selectedFolderId`를 두지 않는다.

## URL 쿼리 설계

나중에 공유 가능한 링크를 위해 선택 상태를 쿼리로 옮길 수 있게 준비한다.

```text
/api-doc?team=...&collection=...&folder=...&request=...
```

1차 구현에서는 내부 state만 써도 되지만, 타입과 API 응답에는 id가 안정적으로 들어가야 한다.
