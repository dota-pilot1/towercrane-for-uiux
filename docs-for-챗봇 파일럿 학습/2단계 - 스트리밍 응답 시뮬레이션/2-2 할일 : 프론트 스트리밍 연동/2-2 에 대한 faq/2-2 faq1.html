2-2 FAQ — 프론트 스트리밍 연동

2단계 노트 · React + Fetch ReadableStream 스트리밍 구현 질문 정리

Q. res.body!.getReader()가 뭔가?

HTTP 응답 body를 스트리밍으로 읽는 Reader를 꺼내는 것이다.

res           → fetch()가 반환한 Response 객체
res.body      → ReadableStream — 바이트가 조금씩 흘러들어오는 "수도꼭지"
.getReader()  → 그 수도꼭지에 꽂는 "빨대" — 청크 단위로 읽음
!             → TypeScript에서 body가 null일 리 없다고 단언
일반 res.json() / res.text()는 응답이 전부 도착해야 반환된다.
GPT 스트리밍처럼 서버가 글자를 조금씩 흘려보낼 때는 다 올 때까지 기다리면 안 되기 때문에,
getReader()로 청크가 도착할 때마다 즉시 처리한다.

Q. new TextDecoder()는 왜 필요한가?

reader.read()가 반환하는 value는 Uint8Array(바이트 배열)다.
네트워크는 사람이 읽을 수 없는 숫자 배열로 데이터를 전송하기 때문에,
TextDecoder가 이걸 문자열로 변환해준다.

// reader.read()가 주는 것
Uint8Array([236, 149, 136, 235, 133, 149, 237, 149, 152, ...])

// TextDecoder.decode() 후
"안녕하세요"
reader가 바이트를 꺼내는 도구라면,
decoder는 그 바이트를 읽을 수 있는 글자로 번역하는 도구다.

Q. done 체크와 [DONE] 체크가 둘 다 있는데 뭐가 다른가?

두 개는 레이어가 다르다.

done: true[DONE] 문자열
누가 만드냐브라우저 (TCP 레벨)서버 코드
의미TCP 연결 자체가 끊김"GPT 응답 완료" 신호
없으면무한 루프 위험응답 끝 감지 못함
// 정상 흐름
서버가 data: [DONE] 전송  →  [DONE] 체크에서 return
(done: true는 그 직후 자동으로 따라옴)

// 비정상 흐름 (서버 크래시, 네트워크 오류)
서버가 [DONE] 없이 연결 끊음  →  done: true에서 break
[DONE]은 "정상 완료", done은 "어떤 이유든 연결 끊김"
— 안전망이 두 겹인 셈이다.

Q. if (!line.startsWith('data: ')) continue 에서 else가 없어도 되나?

continue가 else 역할을 한다.
조건 불만족 시 다음 반복으로 점프하기 때문에 아래 코드는 실행되지 않는다.

// 아래 둘은 완전히 동일한 동작

// else 없는 버전 (early continue 패턴)
if (!line.startsWith('data: ')) continue
const payload = line.slice(6)

// else 있는 버전
if (line.startsWith('data: ')) {
  const payload = line.slice(6)
}
else 없는 쪽이 들여쓰기가 줄어서 더 읽기 쉽다.
이 패턴을 early continue(조기 탈출)라고 부르며 실무에서 자주 쓴다.

Q. prev.map() 안에서 특정 메시지만 업데이트하는 코드가 왜 이렇게 생겼나?

setMessages((prev) =>
  prev.map((m) =>
    m.id === assistantMsgId
      ? { ...m, content: m.content + chunk }  // 이 메시지만 텍스트 누적
      : m                                      // 나머지는 그대로
  )
)

React는 불변성을 요구하기 때문에 직접 수정(m.content += chunk) 대신
새 객체를 만들어 교체하는 방식을 쓴다.

{ ...m, content: m.content + chunk }

...m → id, role, timestamp 등 나머지 필드는 그대로 복사
content: ... → content 필드만 덮어씀

몇 번째인지(인덱스)가 아니라 id로 특정하기 때문에,
대화가 쌓여서 배열이 아무리 길어져도 정확히 그 메시지만 업데이트된다.

Q. AI 응답 메시지를 미리 빈 껍데기로 만들어 놓는 이유가 뭔가?

// 전송 버튼 클릭 시점에 빈 껍데기를 미리 배열에 추가
const assistantMsg: Message = {
  id: assistantMsgId,
  role: 'assistant',
  content: '',          ← 빈 껍데기
  timestamp: new Date(),
}
setMessages((prev) => [...prev, userMsg, assistantMsg])
만약 이렇게 안 하고 청크마다 새 메시지를 추가하면
AI 메시지가 청크 수만큼 여러 개 생겨버린다.

자리를 먼저 잡고 → 같은 자리를 업데이트하는 방식이라
화면에는 하나의 메시지가 타이핑되듯 채워지는 것처럼 보인다. 
전송 직후:  AI: ""
청크 "안":  AI: "안"
청크 "녕":  AI: "안녕"
청크 "하세요": AI: "안녕하세요"  ← 같은 자리

Q. 흐름이 현란한데, Svelte라면 더 깔끔하게 구현할 수 있나?

Svelte를 써도 스트리밍 로직 자체는 거의 동일하다.
현란함의 원인은 React 때문이 아니라 스트리밍 프로토콜 자체다.

부분ReactSvelte
getReader() / TextDecoder동일동일 (브라우저 API)
done / [DONE] 이중 체크동일동일
상태 업데이트setMessages(prev => prev.map(...))messages = messages.map(...)
불변성 요구있음 (새 객체 생성 필수)없음 (직접 수정 가능)
Svelte는 불변성 강제가 없어서 상태 업데이트 한 줄이 조금 단순해진다.
하지만 getReader(), TextDecoder, done/[DONE] 처리,
빈 껍데기 먼저 추가하는 패턴은 프레임워크와 무관하게 동일하게 필요하다.

현란함의 본질은 "스트리밍 데이터를 실시간으로 특정 UI 요소에 누적하는 문제"이고,
이건 어느 프레임워크를 써도 피할 수 없다.

핵심 로직 2개

이 구현 전체는 결국 이 두 줄의 조합이다.

① 자리 먼저 잡기 — 빈 껍데기를 배열에 추가

setMessages((prev) => [...prev, userMsg, assistantMsg])
//                                        ↑ content: '' — 빈 껍데기
전송 버튼을 누른 순간, 사용자 메시지와 AI 응답 자리를 동시에 배열에 추가한다.
AI 응답은 아직 비어있지만 id는 이미 확정된 상태.
이 id가 다음 로직의 열쇠가 된다.

② 그 자리만 업데이트 — 청크가 올 때마다 누적

setMessages((prev) =>
  prev.map((m) =>
    m.id === assistantMsgId
      ? { ...m, content: m.content + chunk }  // 이 자리만 텍스트 누적
      : m                                      // 나머지는 그대로
  )
)
청크가 올 때마다 ①에서 잡아둔 자리를 찾아서 텍스트를 이어 붙인다.
전체 배열을 새로 만들지 않고 해당 메시지 하나만 새 객체로 교체하는 방식.

①이 없으면 ②가 찾을 자리가 없고, ②가 없으면 ①은 영원히 빈 껍데기로 남는다. 
// 두 로직이 협력하는 전체 그림

전송 클릭 → ① { id:'112', content:'' } 배열에 추가

청크 "안"   도착 → ② id:'112' 찾아서 content: "안"
청크 "녕"   도착 → ② id:'112' 찾아서 content: "안녕"
청크 "하세요" 도착 → ② id:'112' 찾아서 content: "안녕하세요"
[DONE]      도착 → isStreaming = false

전체 흐름 한 번에 정리

① 전송 버튼 클릭
   → assistantMsgId 생성
   → 배열에 userMsg + assistantMsg(빈 껍데기) 추가   ← 핵심 로직 ①
        ↓
② fetch POST → res.body.getReader() 로 빨대 꽂기
        ↓
③ while(true) 루프
   → reader.read() → Uint8Array 청크 수신
   → TextDecoder.decode() → 문자열 변환
   → split('\n') → SSE 라인 파싱
        ↓
④ 'data: '로 시작하는 라인만 처리
   → [DONE] 이면 isStreaming = false → return
   → 아니면 JSON 파싱 → chunk 추출
        ↓
⑤ setMessages(prev => prev.map(...))
   → id가 assistantMsgId인 메시지만 content 누적   ← 핵심 로직 ②
   → 나머지는 그대로
        ↓
⑥ done: true → 루프 break (연결 끊김 안전망)
