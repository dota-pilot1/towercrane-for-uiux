3-3 — DB 연동 구현 계획

세션과 메시지를 SQLite DB에 저장 · 새로고침해도 유지되는 진짜 챗봇 구조

목표

Zustand persist(localStorage) → 백엔드 DB 저장으로 전환.
새로고침, 브라우저 변경, 캐시 삭제와 무관하게 대화가 영구 보존된다.

(유저별 분리는 3-4에서 추가)

전체 구조 변경 그림

// 3-2 (Zustand persist)
사용자  ──→  Zustand store  ──→  localStorage

// 3-3 (DB 연동)
사용자  ──→  Zustand store  ──→  fetch API  ──→  NestJS  ──→  SQLite
                ↑                                              │
                └──────────────  응답으로 반환  ────────────────┘

1. 백엔드 — DB 스키마 추가

schema.ts

export const chatSessionsTable = sqliteTable('chat_sessions', {
  id: text('id').primaryKey(),
  title: text('title').notNull(),
  createdAt: text('created_at').notNull(),
  updatedAt: text('updated_at').notNull(),
})

export const chatMessagesTable = sqliteTable('chat_messages', {
  id: text('id').primaryKey(),
  sessionId: text('session_id').notNull()
    .references(() => chatSessionsTable.id, { onDelete: 'cascade' }),
  role: text('role').$type<'user' | 'assistant'>().notNull(),
  content: text('content').notNull(),
  createdAt: text('created_at').notNull(),
})
핵심 포인트:
  • chat_messages.session_id → chat_sessions.id 외래키
  • onDelete: 'cascade' — 세션 삭제 시 메시지도 자동 삭제
  • role은 'user' | 'assistant' 두 값만 가능

2. 백엔드 — API 엔드포인트 설계

메소드경로역할
GET/chatbot/sessions세션 목록 조회 (최신순)
POST/chatbot/sessions새 세션 생성
PATCH/chatbot/sessions/:id세션 이름 변경
DELETE/chatbot/sessions/:id세션 삭제 (메시지도 함께)
GET/chatbot/sessions/:id/messages해당 세션의 메시지 전체
POST/chatbot/stream스트리밍 + 메시지 자동 저장

스트리밍 API의 새로운 책임

POST /chatbot/stream
Body: { sessionId, message }

서버가 하는 일:
① 세션 조회 + updatedAt 갱신 + 첫 메시지면 title 자동 설정
② user 메시지 DB 저장
③ 클라이언트에 meta 이벤트 전송 (저장된 user id + 갱신된 title)
④ OpenAI 스트리밍 시작 → 텍스트 청크 클라이언트에 전송 + 누적
⑤ 완성된 assistant 메시지 DB 저장
⑥ done 이벤트 전송 (저장된 assistant id)
⑦ [DONE] 전송
스트리밍 응답에 3가지 이벤트 타입이 섞여 나간다:
  • { type: 'meta', userMessage, sessionTitle } — 시작 시
  • { text: '청크' } — 스트리밍 중
  • { type: 'done', assistantMessage } — 완료 시
프론트는 type 필드로 분기해서 처리.

4. 메시지 전송 흐름 — temp id → server id 교체 패턴

STEP 1 — temp id로 즉시 화면에 표시
const tempUserId = `temp-user-${Date.now()}`
const tempAssistantId = `temp-assistant-${Date.now()}`

appendLocalMessage(activeId, { id: tempUserId, role: 'user', content: text, ... })
appendLocalMessage(activeId, { id: tempAssistantId, role: 'assistant', content: '', ... })
STEP 2 — meta 이벤트 수신 → user temp id를 server id로 교체
if (parsed.type === 'meta') {
  replaceLocalMessage(activeId, tempUserId, {
    id: parsed.userMessage.id,    ← server가 저장한 id
    role: 'user',
    content: parsed.userMessage.content,
    timestamp: new Date(parsed.userMessage.createdAt),
  })
  setSessionTitle(activeId, parsed.sessionTitle)
}
STEP 3 — 텍스트 청크 누적 (temp id 그대로)
else if ('text' in parsed) {
  updateLocalChunk(activeId, tempAssistantId, parsed.text)
}
STEP 4 — done 이벤트 수신 → assistant temp id를 server id로 교체
else if (parsed.type === 'done') {
  replaceLocalMessage(activeId, tempAssistantId, {
    id: parsed.assistantMessage.id,
    ...
  })
}
왜 temp id를 쓰는가?
서버가 메시지를 저장하기 전에 화면에 먼저 보여줘야 사용자 체감 속도가 빠르다.
나중에 서버가 보낸 진짜 id로 갈아끼우는 방식 = Optimistic UI 패턴.
