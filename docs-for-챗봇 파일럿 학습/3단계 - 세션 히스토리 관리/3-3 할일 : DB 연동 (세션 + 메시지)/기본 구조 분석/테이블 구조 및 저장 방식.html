3-3 — 테이블 구조 및 저장 방식

SQLite 두 테이블 + 외래키 cascade + 메시지 저장 타이밍

📌 핵심 요약

① 두 테이블 — chat_sessions (대화방), chat_messages (말풍선)
② 1:N 관계 — 세션 하나에 여러 메시지
③ cascade 삭제 — 세션 지우면 메시지도 자동 삭제
④ assistant 저장 타이밍 — 청크마다가 아니라 완성본 한 번만

1. chat_sessions — 대화방 테이블

export const chatSessionsTable = sqliteTable('chat_sessions', {
  id: text('id').primaryKey(),
  title: text('title').notNull(),
  createdAt: text('created_at').notNull(),
  updatedAt: text('updated_at').notNull(),
})
컬럼타입역할
idTEXT PRIMARY KEY UUID v4 — randomUUID() 로 생성
titleTEXT NOT NULL 사이드바에 표시. 기본 "새 대화", 첫 메시지로 자동 변경
created_atTEXT NOT NULL 세션 만든 시각 (ISO 8601 문자열)
updated_atTEXT NOT NULL 마지막 활동 시각 — 목록 정렬 기준
왜 Date 타입이 아닌 TEXT?
SQLite는 Date 타입이 없다. 모든 시각은 ISO 8601 문자열로 저장한다.
'2026-05-24T05:18:13.000Z' 형태로 들어간다.

2. chat_messages — 말풍선 테이블

export const chatMessagesTable = sqliteTable('chat_messages', {
  id: text('id').primaryKey(),
  sessionId: text('session_id').notNull()
    .references(() => chatSessionsTable.id, { onDelete: 'cascade' }),
  role: text('role').$type<'user' | 'assistant'>().notNull(),
  content: text('content').notNull(),
  createdAt: text('created_at').notNull(),
})
컬럼타입역할
idTEXT PRIMARY KEY UUID v4
session_idTEXT FK chat_sessions(id) 참조. cascade 삭제
roleTEXT NOT NULL 'user' 또는 'assistant' — Drizzle $type 로 제한
contentTEXT NOT NULL 메시지 본문. assistant는 스트리밍 누적 완성본
created_atTEXT NOT NULL 생성 시각 — 메시지 정렬 기준 (오름차순)

3. 두 테이블의 관계 — 1:N + cascade

chat_sessions (1)                     chat_messages (N)
  ┌─────────────────────────┐           ┌──────────────────────────┐
  │ id: 7f3a-...            │ ◄──────── │ session_id: 7f3a-...      │
  │ title: "안녕"            │           │ role: 'user'             │
  │ createdAt: ...          │           │ content: "안녕"          │
  │ updatedAt: ...          │           └──────────────────────────┘
  └─────────────────────────┘           ┌──────────────────────────┐
                                        │ session_id: 7f3a-...      │
                                        │ role: 'assistant'        │
                                        │ content: "안녕하세요!"   │
                                        └──────────────────────────┘

cascade 삭제의 의미

DELETE FROM chat_sessions WHERE id = '7f3a-...'

       ↓ 자동으로 함께 실행

DELETE FROM chat_messages WHERE session_id = '7f3a-...'
애플리케이션 코드에서 메시지를 따로 지울 필요가 없다.
SQL 레벨에서 ON DELETE CASCADE 가 작동한다.

전제 조건: SQLite에서 PRAGMA foreign_keys = ON 설정이 켜져 있어야 함.
→ database.service.ts 의 onModuleInit 에서 활성화한다.

4. 스토어 메시지 ↔ DB 매핑

📌 핵심

스토어의 messages 배열이 통째로 DB에 들어가는 게 아니라,
배열의 각 원소가 chat_messages 한 행씩으로 저장된다.

객체 1개 ↔ 컬럼 매핑

// 프론트 store의 메시지 객체
{
  id: '7f3a-...',
  role: 'user',
  content: '안녕',         ← 이게
  timestamp: Date,
}

       ↓ INSERT

// DB chat_messages 1행
| id         | session_id | role | content | created_at     |
| 7f3a-...   | 7f3a-...   | user | 안녕    | 2026-05-24... |
                                  ↑ 여기로
스토어 필드DB 컬럼변환
idid그대로
(상위 세션의 id)session_idFK로 연결
rolerole그대로 ('user' / 'assistant')
contentcontent그대로 (문자열)
timestamp (Date)created_at (TEXT)ISO 문자열로 변환

배열 → 여러 행

// store
messages: [
  { id: '1', role: 'user',      content: '안녕' },           ← messages[0]
  { id: '2', role: 'assistant', content: '안녕하세요!' },    ← messages[1]
  { id: '3', role: 'user',      content: '오늘 날씨' },      ← messages[2]
]

       ↓ 각각 INSERT

// DB chat_messages (3행)
| id | session_id | role      | content       |
| 1  | 7f3a-...   | user      | 안녕          |   ← messages[0]
| 2  | 7f3a-...   | assistant | 안녕하세요!   |   ← messages[1]
| 3  | 7f3a-...   | user      | 오늘 날씨     |   ← messages[2]
배열 길이만큼 행이 쌓이는 구조다.
배열 자체를 통째로 한 컬럼에 JSON으로 저장하는 게 아니다.

assistant content는 어디서 오는가 (= DB에 저장되는 챗봇 응답 메시지)

// 백엔드 streamGpt 내부
let assistantContent = ''                ← 메모리 변수

for await (const chunk of stream) {
  const text = chunk.choices[0]?.delta?.content ?? ''
  if (text) {
    assistantContent += text             ← 청크들을 이어붙임
    res.write(`data: ${JSON.stringify({ text })}\n\n`)
  }
}

// 완성된 한 줄을 content 컬럼에 한 번 INSERT
this.insertMessage(sessionId, 'assistant', assistantContent)
                                            ↑ 이게 DB content 컬럼으로
스트리밍으로 들어온 청크 수십 개가 메모리에서 한 문자열로 합쳐진 뒤,
그 합본이 content 컬럼에 한 번 INSERT 된다.

조회 시 역방향 매핑

// DB → 프론트 store

DB row              →  DTO              →  store Message
─────────────────────────────────────────────────────────
id          : '1'   →  id          : '1' →  id        : '1'
session_id  : 'X'   →  sessionId   : 'X' →  (사용 안 함)
role        : 'user'→  role        : 'user' →  role    : 'user'
content     : '안녕' → content     : '안녕' →  content : '안녕'
created_at  : 'ISO' →  createdAt   : 'ISO' →  timestamp : new Date(ISO)
핵심 변환 포인트는 created_at (TEXT) → timestamp (Date).
나머지는 거의 이름만 바뀌거나 그대로 들어간다.
변환은 toMessage() 함수에서 일어난다.

5. 저장 방식 — 언제, 어떻게 저장하나

저장 4가지 경로

대상저장 시점저장 방식호출 위치
chat_sessions 새 행 "+" 버튼 클릭 INSERT 1번 POST /chatbot/sessions
chat_sessions 갱신 이름 변경 / 메시지 전송 시 UPDATE 1번 PATCH / touchSession()
chat_messages user 스트리밍 시작 직전 INSERT 1번 streamGpt() 내부
chat_messages assistant 스트리밍 완료 직후 INSERT 1번 (완성본) streamGpt() 내부
📌 보충 — 메시지 전송 1회에 DB 쓰기는 정확히 3번

표의 마지막 세 줄(chat_sessions 갱신 + user INSERT + assistant INSERT)이
한 번의 메시지 전송에서 모두 일어나는 동작이다.

청크가 100개 흘러와도 DB 쓰기는 3번 — 청크는 메모리 변수에 누적만 하기 때문. 
POST /chatbot/stream { sessionId, message: '안녕' }
       ↓
[T+10]   touchSession()
         → ① UPDATE chat_sessions  (title, updated_at 갱신)
       ↓
[T+20]   insertMessage('user', ...)
         → ② INSERT chat_messages  (user 메시지)
       ↓
[T+30]   meta 이벤트 전송 (DB 쓰기 X)
       ↓
[T+50~3000]  OpenAI 청크 누적 — 메모리 += 만, DB 쓰기 X
       ↓
[T+3010] insertMessage('assistant', ...)
         → ③ INSERT chat_messages  (assistant 완성본)
       ↓
[T+3020] done + [DONE] 전송 (DB 쓰기 X)
#작업SQL
①세션 갱신UPDATE chat_sessions
②user 메시지 저장INSERT chat_messages
③assistant 메시지 저장INSERT chat_messages
핵심: 스트리밍 길이와 DB 쓰기 횟수는 무관하다.
GPT가 100자를 토해내든 10,000자를 토해내든 DB 쓰기는 3번으로 고정.

5. ★ assistant 저장 타이밍 — 핵심 포인트

GPT는 토큰을 수십~수백 개의 청크로 흘려보낸다.
그런데 우리는 완성된 한 줄을 단 한 번만 DB에 저장한다.

청크마다 저장하지 않는다.

잘못된 방법 — 청크마다 저장

// ❌ 안 좋은 패턴
for await (const chunk of stream) {
  const text = chunk.choices[0]?.delta?.content ?? ''
  if (text) {
    this.db.insert(chatMessagesTable).values({ ... text ... }).run()
    // 매 청크마다 INSERT → 수십~수백 번 DB 쓰기
  }
}
문제:
  • 토큰 하나에 디스크 쓰기 1회 → 수십~수백 번 발생
  • SQLite도 부담, 디스크 I/O 폭발
  • 중간 청크 단위로 행이 쪼개져서 조회 시 합쳐야 함

좋은 방법 — 메모리에 누적 후 1번 INSERT

// ✅ 지금 코드 패턴
let assistantContent = ''             ← 메모리 변수

for await (const chunk of stream) {
  const text = chunk.choices[0]?.delta?.content ?? ''
  if (text) {
    assistantContent += text          ← 누적만 (DB X)
    res.write(`data: ${JSON.stringify({ text })}\n\n`)
  }
}

// 스트리밍 끝난 후 완성본을 한 번만 저장
const assistantMessage = this.insertMessage(
  sessionId, 'assistant', assistantContent,
)
결과:
  • DB 쓰기 = 딱 1번
  • 한 메시지 = 한 행
  • 조회할 때 그냥 SELECT 하면 끝

실제 코드 위치

towercrane-for-uiux-server/src/chatbot/chatbot.service.ts

라인 160:    let assistantContent = '';                       ← 메모리 변수
라인 161-167: for await (const chunk of stream) { ... }       ← 청크 누적
라인 164:      assistantContent += text;                       ← += 로 이어붙임
라인 169-173: this.insertMessage(sessionId,                    ← DB 1번 INSERT
                                 'assistant',
                                 assistantContent);
라인 175:    res.write('... type: "done" ...')                  ← done 이벤트
라인 177:    res.write('data: [DONE]\n\n')                      ← 종료 신호
파일 한 줄 요약: streamGpt() 함수 안에서
메모리 누적 → 한 번 INSERT → done 이벤트 → [DONE] 전송 순서로 진행된다.

6. 메시지 저장 타이밍 — 시간 순서

[T+0]    POST /chatbot/stream { sessionId, message: '안녕' }
[T+10]   touchSession() — 세션 updatedAt 갱신, 첫 메시지면 title 자동 설정
[T+20]   ★ INSERT user 메시지 (DB 쓰기 1)
[T+30]   meta 이벤트 전송 (진짜 user id 알림)
[T+50]   OpenAI 스트리밍 시작
[T+100]  data: { text: '안' }
[T+150]  data: { text: '녕' }
[T+200]  data: { text: '하세요' }
...      (메모리 변수 assistantContent 에 누적만)
[T+3000] 스트리밍 완료
[T+3010] ★ INSERT assistant 메시지 (DB 쓰기 2)
[T+3020] done 이벤트 전송 (진짜 assistant id 알림)
[T+3030] [DONE] 전송 → 연결 종료
3초짜리 대화에서 DB 쓰기는 정확히 2번 (user 1번 + assistant 1번).
세션 갱신 UPDATE 까지 포함하면 총 3번.

7. 정리

구분chat_sessionschat_messages
역할 대화방 메타 실제 메시지
관계 1 (부모) N (자식) — session_id FK
삭제 시 cascade로 자식도 삭제 —
저장 횟수 새 세션 1번 + 갱신 매번 메시지당 1번 (청크 X)
정렬 기준 updated_at DESC (목록) created_at ASC (시간순)
