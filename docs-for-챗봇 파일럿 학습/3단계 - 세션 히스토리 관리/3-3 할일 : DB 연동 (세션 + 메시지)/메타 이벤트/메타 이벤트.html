3-3 — 메타 이벤트 프로세스

"메타 이벤트가 왜 필요한가" 처음부터 끝까지 풀어서 설명

한 줄 요약

서버가 user 메시지를 DB에 저장하면서 받은 진짜 id를 프론트에 알려주는 신호다.
프론트는 그 신호로 화면의 임시 id를 진짜 id로 교체한다.

1. 문제 상황 — 왜 id 교체가 필요한가

프론트는 서버보다 먼저 화면에 메시지를 표시한다

// 사용자가 "안녕" 입력 후 전송 클릭한 순간

[프론트 시각: 0초]
  → "내 메시지가 즉시 화면에 떠야 안 답답함"
  → 근데 아직 서버에 저장도 안 했고 id도 없음
  → 임시 id를 만들어서 일단 화면에 표시

const tempUserId = `temp-user-${Date.now()}`  // "temp-user-1234567890"

appendLocalMessage(activeId, {
  id: tempUserId,        ← 가짜 id
  role: 'user',
  content: '안녕',
  timestamp: new Date(),
})
이 시점 화면 상태:
messages: [{ id: 'temp-user-1234567890', content: '안녕' }]

사용자는 자기 메시지를 즉시 봤지만, 이 id는 백엔드 DB에 존재하지 않는다.

2. 동시에 백엔드는 진짜 id를 만든다

[백엔드 시각: 약 50~200ms 후]
  → POST /chatbot/stream 요청 도착
  → DB에 메시지 저장하면서 진짜 id 생성

const userMessage = this.insertMessage(sessionId, 'user', message)
// 결과: { id: '7f3a-8b2c-...', sessionId, role, content, createdAt }
이 시점에 같은 메시지에 id가 두 개 존재한다:
  • 프론트 화면: temp-user-1234567890
  • 백엔드 DB: 7f3a-8b2c-...
이대로 두면 나중에 충돌이 생긴다.

3. 왜 충돌이 생기나 — 새로고침 시나리오

// 사용자가 새로고침 했을 때

[1] 프론트가 GET /chatbot/sessions/:id/messages 호출
[2] 백엔드가 DB에서 메시지 반환: [{ id: '7f3a-8b2c-...', content: '안녕' }]
[3] 프론트가 화면에 표시

// 만약 새로고침 전에 id 교체를 안 했다면?
화면 메시지: temp-user-1234567890   ← 임시 id로 표시되어 있던 메시지
DB 메시지:   7f3a-8b2c-...           ← 새로고침 후 받아온 메시지

같은 메시지가 두 개로 보이거나, id로 매칭이 안 되거나, 삭제/수정이 안 됨
그래서: 임시 id는 화면 표시용으로만 잠깐 쓰고,
서버가 진짜 id를 만든 즉시 교체해야 한다.

그 교체 신호가 바로 meta 이벤트다.

4. meta 이벤트 — 서버가 보내는 "진짜 id 알림"

백엔드: meta 이벤트 전송

// chatbot.service.ts

async streamGpt(sessionId, message, res) {
  // ① DB에 user 메시지 저장 (진짜 id 부여됨)
  const userMessage = this.insertMessage(sessionId, 'user', message)
  //      ↑ { id: '7f3a-8b2c-...', content: '안녕', ... }

  // ② 프론트에 "방금 저장한 메시지 정보야" 라고 전송
  res.write(`data: ${JSON.stringify({
    type: 'meta',
    userMessage,                    ← 진짜 id 포함
    sessionTitle: meta.title,       ← 자동 설정된 제목
  })}\n\n`)

  // ③ 그 다음 OpenAI 스트리밍 시작 ...
}

프론트: meta 받으면 id 교체

// use-history-chat.ts

const parsed = JSON.parse(payload)

if (parsed.type === 'meta') {
  replaceLocalMessage(activeId, tempUserId, {
    id: parsed.userMessage.id,                ← 진짜 id로 교체
    role: 'user',
    content: parsed.userMessage.content,
    timestamp: new Date(parsed.userMessage.createdAt),
  })
  setSessionTitle(activeId, parsed.sessionTitle)   ← 사이드바 제목도 갱신
}
replaceLocalMessage 는 store 안에서
messages.map(m => m.id === oldId ? newMessage : m) 식으로 해당 메시지 하나만 교체한다.

5. 전체 타임라인

T+0ms — 사용자 전송 클릭
프론트 store:
  messages: [
    { id: 'temp-user-1234', content: '안녕' },        ← 임시
    { id: 'temp-assistant-1235', content: '' },       ← 임시 (빈 껍데기)
  ]
화면: "안녕" 표시됨, AI 응답 자리 비어있음
T+100ms — 백엔드가 DB 저장 + meta 전송
DB:
  chat_messages: [{ id: '7f3a', content: '안녕', role: 'user' }]

SSE 응답:
  data: { type: 'meta', userMessage: { id: '7f3a', ... }, sessionTitle: '안녕' }
T+150ms — 프론트가 meta 받고 id 교체
프론트 store:
  messages: [
    { id: '7f3a', content: '안녕' },              ← 진짜 id로 교체됨!
    { id: 'temp-assistant-1235', content: '' },     ← 아직 임시
  ]
화면: 변화 없음 (사용자는 id가 바뀐 걸 모름)
사이드바: '새 대화' → '안녕' 으로 제목 갱신
T+200~3000ms — OpenAI 스트리밍 청크들
SSE 응답 (반복):
  data: { text: '안' }
  data: { text: '녕' }
  data: { text: '하세요' }

프론트:
  temp-assistant-1235 의 content 에 누적 → "안", "안녕", "안녕하세요"
T+3000ms — 백엔드가 assistant 저장 + done 전송
DB:
  chat_messages: [
    { id: '7f3a', content: '안녕', role: 'user' },
    { id: '9c4b', content: '안녕하세요!', role: 'assistant' },     ← 추가
  ]

SSE 응답:
  data: { type: 'done', assistantMessage: { id: '9c4b', ... } }
  data: [DONE]
T+3050ms — 프론트가 done 받고 assistant id 교체
프론트 store:
  messages: [
    { id: '7f3a', content: '안녕' },
    { id: '9c4b', content: '안녕하세요!' },        ← 진짜 id로 교체됨!
  ]

이제 화면 ↔ DB 가 완전히 일치한다.

6. 정리 — meta 이벤트의 역할

역할설명
① id 동기화 프론트 임시 id를 백엔드 진짜 id로 교체
② 제목 갱신 첫 메시지로 세션 title이 바뀐 걸 프론트에 알려줌
③ 저장 확인 "DB에 저장 성공했어" 라는 묵시적 신호
이벤트 종류 3가지를 다시 보면:
  • type: 'meta' — 시작: user 메시지 저장 완료 + 진짜 id
  • { text } — 중간: GPT 청크
  • type: 'done' — 끝: assistant 메시지 저장 완료 + 진짜 id
세 이벤트의 핵심은 모두 "프론트의 임시 상태를 진짜 DB 상태와 맞춘다"는 점이다.
