3-3 — 메타 정보 전달의 개념

조회와 저장의 흐름은 다르다 · "메타"가 등장하는 이유

📌 두 줄 요약 (이거만 기억해도 됨)

① 조회 = 쌩 조회. 응답 JSON에 이미 진짜 id가 들어있어서 메타가 필요 없음.

② 메시지 전송 시에는 화면에 임시 id로 먼저 그려두고,
   서버가 DB에 저장한 실제 id로 교체하기 위한 응답 데이터를 보낸다.
   → 이 응답을 메타 데이터 응답이라고 부른다.

핵심 개념 한 줄

조회는 그냥 조회다. 메타가 등장하는 건 오직 "저장 + 스트리밍"이 동시에 일어날 때다.

메타 정보 = "임시 id로 화면에 먼저 그려둔 메시지의 진짜 DB id를 알려주는 신호"

1. 조회 — 메타 없음

useEffect(() => {
  if (!loaded) void loadSessions()
}, [loaded, loadSessions])

       ↓ 페이지 마운트

GET /chatbot/sessions     ← 일반 REST API
       ↓
[
  { id: '7f3a-...', title: '안녕', createdAt: '...', updatedAt: '...' },
  { id: '9c4b-...', title: '날씨', createdAt: '...', updatedAt: '...' },
]
       ↓
store.sessions 에 그대로 세팅 끝
  • 응답이 한 번에 온다 (스트리밍 아님)
  • id가 처음부터 진짜 DB id다
  • 프론트가 임시 id를 만든 적이 없으니 교체할 것도 없다
  • → 메타 신호가 필요 없음

2. 저장 + 스트리밍 — 메타 필수

사용자: "안녕" 전송
       ↓
프론트: tempUserId = 'temp-user-1234' 로 화면에 먼저 표시
       ↓ (사용자는 즉시 자기 메시지를 본다 — Optimistic UI)
프론트: POST /chatbot/stream { sessionId, message: '안녕' }
       ↓
백엔드: DB에 user 메시지 저장 → 진짜 id = '7f3a-...' 생성
       ↓
       "야 프론트, 너 화면에 temp-user-1234 라고 띄워둔 거 있지?
        그거 진짜 id는 7f3a-... 야"
       ↓
       data: { type: 'meta', userMessage: { id: '7f3a-...', ... } }
       ↓
프론트: temp-user-1234 → 7f3a-... 로 교체
  • 응답이 청크 단위로 흘러나온다 (스트리밍)
  • 프론트가 응답 기다리는 동안 답답하지 않게 임시 id로 미리 그렸다
  • 서버가 DB에 저장하면서 만든 진짜 id를 알려줘야 함
  • → 그 알림이 메타 이벤트

3. 비유 — 음식점 주문

조회 (메뉴 보기)저장 + 스트리밍 (주문)
흐름 메뉴판 한 번 줘서 끝 주문번호 외치고 음식 하나씩 나옴
id 처리 메뉴판에 이미 번호 인쇄됨 "주문 #43번이요!" — 진동벨 받기
메타 정보 필요 없음 주문번호 알림 (= 메타)
음식점에서 카운터에 "주문 #43번이요" 라고 외치는 게 메타 이벤트와 같다.
손님은 영수증의 임시 번호로 진동벨을 들고 있다가, 진짜 주문번호 호출되면 그제야 카운터로 간다.

4. 왜 굳이 임시 id를 쓰는가

// 만약 임시 id 없이 서버 응답만 기다리면?

사용자: 전송 클릭
       ↓
[화면 멈춤] ← 1~3초 동안 아무것도 안 보임
       ↓
서버 응답 도착
       ↓
화면에 메시지 표시
// 임시 id + 메타 패턴 (지금 구조)

사용자: 전송 클릭
       ↓
[즉시 화면에 표시] ← temp id로 그림 (0ms)
       ↓
서버가 진짜 id 알려줌 (50~100ms)
       ↓
[티 안 나게 id만 교체] ← 사용자는 모름
결국 메타 정보 전달은:
"속도를 위해 거짓말로 미리 그려둔 화면을, 나중에 진실로 살짝 갈아끼우기 위한 신호"

5. 정리

상황API 형태id 처리메타 필요?
페이지 진입 (세션 목록) GET — JSON 한 방 응답에 진짜 id 포함 ❌
세션 클릭 (메시지 조회) GET — JSON 한 방 응답에 진짜 id 포함 ❌
세션 생성/삭제/이름변경 POST/DELETE/PATCH — JSON 응답에 진짜 id 포함 ❌
메시지 전송 (스트리밍) POST — SSE 스트림 temp id → server id 교체 필요 ✅ meta + done
메타가 필요한 단 하나의 조건:
"서버 응답 전에 프론트가 임시 id로 화면을 먼저 그린 경우"

스트리밍 + Optimistic UI 조합이 아니면 메타는 등장하지 않는다.
