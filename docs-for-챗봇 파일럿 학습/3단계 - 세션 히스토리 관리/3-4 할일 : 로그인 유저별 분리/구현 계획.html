3-4 — 로그인 유저별 분리 구현 계획

JWT 인증 가드로 유저별 대화 분리 · 농협 프로젝트 실무 패턴

목표

3-3까지는 모든 사용자가 같은 세션 목록을 본다.
3-4에서는 로그인한 유저별로 대화가 완전히 분리된다.

A 유저가 만든 세션은 B 유저에게는 보이지 않고,
타인의 세션 id로 API를 호출해도 거부된다.

전제 — 기존 인증 인프라 활용

TasksModule처럼 imports: [AuthModule] 로 가드를 쓸 수 있다.
토큰은 프론트의 useSessionStore 가 이미 관리 중이며
apiRequest 가 자동으로 Authorization: Bearer ... 헤더를 붙인다.

1. 백엔드 — 스키마에 userId 추가

export const chatSessionsTable = sqliteTable('chat_sessions', {
  id: text('id').primaryKey(),
  userId: text('user_id')
    .notNull()
    .references(() => usersTable.id, { onDelete: 'cascade' }),
  title: text('title').notNull(),
  createdAt: text('created_at').notNull(),
  updatedAt: text('updated_at').notNull(),
})
마이그레이션 주의:
3-3에서 만든 기존 데이터에는 user_id 가 없다.
옵션:
① 기존 chat_sessions 데이터 삭제 후 재생성 (학습용이라 OK)
② ALTER TABLE 로 컬럼 추가 + 기본값으로 admin id 채우기

2. 백엔드 — Controller에 가드 적용

@UseGuards(AuthGuard)
@Controller('chatbot')
export class ChatbotController {
  @Get('sessions')
  listSessions(@CurrentUser() user: User) {
    return this.chatbotService.listSessions(user.id)
  }

  @Post('sessions')
  createSession(@CurrentUser() user: User, @Body() body) {
    return this.chatbotService.createSession(user.id, body?.title)
  }

  ...
}
모든 엔드포인트에 가드 적용 → 인증 안 된 요청은 401 반환
@CurrentUser() 데코레이터로 토큰에서 추출된 유저 정보를 받는다

3. 백엔드 — Service에 userId 필터 + 권한 검증

조회 시 userId 필터

listSessions(userId: string) {
  return this.db
    .select()
    .from(chatSessionsTable)
    .where(eq(chatSessionsTable.userId, userId))   ← 본인 것만
    .orderBy(desc(chatSessionsTable.updatedAt))
    .all()
}

수정/삭제 시 소유자 검증

private assertOwnership(sessionId: string, userId: string) {
  const session = this.db.select().from(chatSessionsTable)
    .where(eq(chatSessionsTable.id, sessionId)).get()
  if (!session) throw new NotFoundException('session not found')
  if (session.userId !== userId) throw new ForbiddenException()
  return session
}

deleteSession(id: string, userId: string) {
  this.assertOwnership(id, userId)
  this.db.delete(chatSessionsTable).where(eq(chatSessionsTable.id, id)).run()
}
왜 별도 검증이 필요한가?
URL 파라미터로 들어온 sessionId 는 누구의 것인지 알 수 없다.
로그인 유저의 토큰만 검증하면 타인 세션 id로 삭제 요청이 통과될 수 있다.
→ 항상 "이 세션이 정말 이 유저 것인가?"를 확인해야 한다.

4. 프론트 — 거의 변경 없음

apiRequest 가 이미 토큰을 자동으로 붙이기 때문에
프론트 코드는 거의 손댈 게 없다.

변경 필요한 부분:
  • 로그인하지 않은 상태에서 페이지 진입 시 처리 (리다이렉트 또는 안내)
  • 토큰 만료(401) 시 store 초기화 (이미 apiRequest에 구현되어 있음)
  • 로그아웃 시 store의 sessions/messagesBySession 초기화

5. 작업 순서

  1. 백엔드 schema.ts 의 chatSessionsTable 에 userId 추가
  2. 백엔드 database.service.ts CREATE TABLE 에 user_id 컬럼 추가
  3. 기존 chat_sessions, chat_messages 데이터 초기화 (학습용)
  4. 백엔드 chatbot.module.ts 에 AuthModule import
  5. 백엔드 chatbot.controller.ts 전체에 @UseGuards(AuthGuard) 적용
  6. 각 컨트롤러 메소드에 @CurrentUser() 추가
  7. 백엔드 chatbot.service.ts 의 모든 메소드에 userId 파라미터 추가
  8. listSessions 에 userId 필터 적용
  9. 수정/삭제/메시지 조회/스트리밍 에 assertOwnership 호출 추가
  10. 프론트 로그아웃 시 store 초기화 로직 추가
  11. 두 명의 테스트 계정으로 대화 분리 확인

7. 농협 프로젝트 적용 포인트

실무에서 이 패턴이 그대로 쓰인다:
  • 감사 대응 — 누가 언제 어떤 대화를 했는지 user_id로 추적 가능
  • 관리자 모니터링 — role === 'admin' 일 때만 전체 조회 허용
  • 보안 — 토큰 + 소유자 검증 이중 방어
  • 다중 기기 — 같은 유저가 다른 기기에서 접속해도 대화 동기화
