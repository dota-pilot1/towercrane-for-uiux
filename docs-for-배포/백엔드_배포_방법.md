# 백엔드 배포 방법

> 대상: `towercrane-for-uiux-server`  
> 방식: EC2 접속 → `main` pull → NestJS build → PM2 restart

## 배포 정보

| 항목 | 값 |
|---|---|
| EC2 Public IP | `54.180.215.129` |
| SSH User | `ubuntu` |
| SSH Key | `docs-for-배포/hibot-d-server-key.pem` |
| API 도메인 | `https://api.hibot-docu.com/api` |
| 앱 포트 | `4001` |
| PM2 앱 이름 | `towercrane-back` |
| DB | SQLite |
| 기본 DB 파일 | `./data/towercrane-catalog.sqlite` |
| SQL 연습장 DB 파일 | `./data/sql-practice/runtime/practice.sqlite` |

## 언제 백엔드를 배포하나

- controller/service/module 변경
- DB schema 또는 초기 seed/migration 로직 변경
- 프론트가 새 API나 새 response field에 의존
- 서버 `.env` 변경
- 파일 업로드, AI API, 인증 등 서버 런타임 설정 변경

프론트가 새 백엔드 동작에 의존하면 백엔드를 먼저 배포하고 API 응답을 확인한 뒤 프론트를 배포합니다.

## SSH 접속

```bash
cd docs-for-배포
chmod 400 hibot-d-server-key.pem
ssh -i hibot-d-server-key.pem ubuntu@54.180.215.129
```

## 최초 배포

```bash
cd ~
git clone https://github.com/dota-pilot1/towercrane-for-uiux.git towercrane
cd ~/towercrane/towercrane-for-uiux-server

cat > .env << 'EOF'
PORT=4001
DATABASE_FILE=./data/towercrane-catalog.sqlite
SQL_PRACTICE_DB_FILE=./data/sql-practice/runtime/practice.sqlite
SQL_PRACTICE_SEED_FILE=
SQL_PRACTICE_MAX_ROWS=500
SQL_PRACTICE_MAX_QUERY_LENGTH=10000
AWS_ACCESS_KEY_ID=<서버에서만_관리>
AWS_SECRET_ACCESS_KEY=<서버에서만_관리>
AWS_S3_BUCKET_NAME=hibot-docu
AWS_S3_REGION=ap-northeast-2
GEMINI_API_KEY=
OPENAI_API_KEY=
EOF

mkdir -p data
npm install
npm run build
pm2 start dist/main.js --name towercrane-back
pm2 save
```

## 코드 업데이트 재배포

서버 배포는 원격 `main` 기준입니다. 로컬 변경이 아직 push되지 않았다면 먼저 GitHub에 반영합니다.

권장 명령:

```bash
./scripts/deploy-backend.sh
```

스크립트가 수행하는 안전장치:

- EC2에서 `/tmp/towercrane-backend-deploy.lock`을 잡아 동시 배포 방지
- 배포 직전 커밋을 `/tmp/towercrane-backend-rollback-commit`에 기록
- SQLite DB 파일을 `data/backups/`에 백업
- `pnpm-lock.yaml`이 있으면 `pnpm install --frozen-lockfile` 우선 사용
- PM2 재시작 후 `https://api.hibot-docu.com/api/menus` 헬스체크
- 헬스체크 실패 시 직전 커밋으로 checkout/build/restart 롤백 시도

## 원격 빌드 지연/SSH 타임아웃 대응

현재 스크립트는 운영 EC2 내부에서 의존성 설치와 `nest build`를 직접 실행합니다. `t3.small` 같은 작은 인스턴스에서는 빌드가 CPU/메모리를 오래 점유하면서 운영 API와 SSH 응답이 같이 느려질 수 있습니다.

### 증상

```text
> nest build
# 이후 수 분간 출력 없음

Connection timed out during banner exchange
curl: (28) Connection timed out
```

### 1차 확인

로컬에서 API와 SSH를 각각 짧은 타임아웃으로 확인합니다.

```bash
curl -fsSI --max-time 15 https://api.hibot-docu.com/api/menus | sed -n '1,20p'

ssh -i docs-for-배포/hibot-d-server-key.pem \
  -o ConnectTimeout=20 \
  -o ServerAliveInterval=5 \
  -o ServerAliveCountMax=2 \
  ubuntu@54.180.215.129 \
  'uptime; pm2 status towercrane-back'
```

SSH가 붙으면 빌드 프로세스와 PM2 상태를 확인합니다.

```bash
ps -eo pid,ppid,etime,stat,%cpu,%mem,cmd \
  | grep -E 'nest build|pnpm build|npm run build|node /home/ubuntu/towercrane' \
  | grep -v grep

pm2 status towercrane-back
pm2 logs towercrane-back --lines 80
```

운영 API가 이미 타임아웃이고 빌드가 장시간 지속되면 배포 빌드 프로세스를 중단한 뒤 기존 PM2 앱이 살아 있는지 확인합니다.

```bash
pkill -f '@nestjs/cli/bin/nest.js build' || true
pkill -f 'pnpm build' || true
pkill -f 'npm run build' || true
pm2 status towercrane-back
curl -fsSI https://api.hibot-docu.com/api/menus | sed -n '1,20p'
```

### SSH도 붙지 않을 때

SSH가 banner 단계에서 타임아웃되면 운영 서버 내부 명령을 실행할 수 없습니다. 이때는 AWS 권한으로 복구해야 합니다.

필요 권한:

- `ec2:DescribeInstanceStatus`
- `ec2:RebootInstances`
- 가능하면 `ssm:DescribeInstanceInformation`, `ssm:SendCommand`

재부팅 권한이 있으면 마지막 수단으로 인스턴스를 재부팅합니다.

```bash
AWS_REGION=ap-northeast-2 \
aws ec2 reboot-instances --instance-ids i-0ade38b8820c356f1
```

재부팅 후 SSH가 붙으면 PM2가 살아났는지 확인합니다.

```bash
ssh -i docs-for-배포/hibot-d-server-key.pem ubuntu@54.180.215.129 \
  'pm2 status towercrane-back; curl -fsSI http://127.0.0.1:4001/api/menus | sed -n "1,20p"'
```

### 재시도 기준

운영 API가 회복되기 전에는 같은 스크립트를 재실행하지 않습니다. 다시 배포해야 한다면 아래 중 하나를 먼저 선택합니다.

- EC2 사양을 일시적으로 올린 뒤 재배포
- 서버에 swap을 추가한 뒤 재배포
- 로컬/CI에서 백엔드 빌드 산출물을 만든 뒤 EC2에는 산출물만 업로드
- `scripts/deploy-backend.sh`에 빌드 timeout과 실패 시 자동 프로세스 정리를 추가

이번 계정으로 복구하려면 최소한 `ec2:RebootInstances` 권한이 필요합니다. SSM으로 SSH 없이 명령 실행까지 하려면 SSM agent 설치 여부와 `ssm:SendCommand` 권한도 확인해야 합니다.

수동 재배포가 필요할 때만 아래 절차를 사용합니다.

```bash
cd ~/towercrane
git pull origin main

cd towercrane-for-uiux-server
npm install
npm run build
pm2 restart towercrane-back
pm2 save
```

## DB 변경이 포함된 경우

현재 서버는 앱 시작 시 필요한 SQLite 테이블/레거시 마이그레이션을 `DatabaseService`에서 보정합니다. 그래도 DB 변경 배포 전에는 반드시 DB 파일을 백업합니다.

```bash
cd ~/towercrane/towercrane-for-uiux-server
mkdir -p data/backups
cp data/towercrane-catalog.sqlite "data/backups/towercrane-catalog.$(date +%Y%m%d-%H%M%S).sqlite"
```

헤더 메뉴도 같은 SQLite DB의 `menus` 테이블에서 내려옵니다. 신규 메뉴는 코드 배포 후 백엔드가 재시작될 때 `DatabaseService`에서 자동 보정합니다.
예를 들어 SQL 연습장 메뉴는 `section_id='sql'`, `name='SQL 연습장'`, `icon='Database'`로 추가됩니다.

SQL 연습장용 DB는 메인 운영 DB와 별도 파일입니다.

| 파일 | 역할 |
|---|---|
| `data/towercrane-catalog.sqlite` | 사용자, 메뉴, 문서 등 메인 앱 운영 DB |
| `data/sql-practice/runtime/practice.sqlite` | SQL 연습 전용 DB |
| `src/sql-practice/seeds/seed.sql` | SQL 연습장 DB 초기 seed |

`seed.sql` 변경 후 배포하면 SQL 연습장 DB는 다음 API 호출 시 seed hash를 비교해 연습장 DB만 새로 만듭니다. 메인 앱 DB는 건드리지 않습니다.

Drizzle SQL migration을 명시적으로 생성/적용하는 운영 절차가 생기면 이 문서에 별도 단계로 추가합니다.

## PM2 확인

```bash
pm2 list
pm2 logs towercrane-back --lines 80
pm2 describe towercrane-back
```

정상 재시작 후 `status`가 `online`인지 확인합니다.

## nginx 확인

백엔드는 `localhost:4001`로 실행되고 nginx가 `api.hibot-docu.com`을 프록시합니다.

```bash
sudo nginx -t
sudo systemctl reload nginx
```

nginx 설정 파일은 `/etc/nginx/sites-enabled/`에서 확인합니다.

## 배포 후 확인

```bash
curl -fsS https://api.hibot-docu.com/api/menus | head -c 500
curl -fsSI https://api.hibot-docu.com/api/menus | sed -n '1,20p'
```

SQL 연습장 메뉴 반영 확인:

```bash
curl -fsS https://api.hibot-docu.com/api/menus | grep -o 'SQL 연습장'
```

`/api/sql/*`는 로그인 세션이 필요한 보호 API입니다. 운영 화면에서는 `https://hibot-docu.com/sql`에 로그인한 뒤 테이블 정보가 표시되는지 확인합니다.

문제가 있으면 PM2 로그와 nginx 로그를 함께 봅니다.

```bash
pm2 logs towercrane-back --lines 120
sudo tail -n 120 /var/log/nginx/error.log
```

## 롤백

스크립트 배포 중 헬스체크가 실패하면 자동 롤백을 시도합니다. 수동 롤백은 아래 절차를 사용합니다.

```bash
cd ~/towercrane
git log --oneline -5
git checkout <이전_정상_커밋>

cd towercrane-for-uiux-server
npm install
npm run build
pm2 restart towercrane-back
pm2 save
```

롤백 후 다시 `main`으로 복귀해야 할 때는 `git checkout main && git pull origin main`을 실행합니다.

## 주의

- `.env`와 SQLite DB 파일은 git에 포함하지 않습니다.
- DB 파일 삭제는 운영 데이터 유실로 이어집니다.
- `pm2 save`는 서버 재부팅 후 현재 프로세스 구성을 복구하기 위해 필요합니다.
